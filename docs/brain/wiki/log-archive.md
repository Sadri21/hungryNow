- **2026-09-09** — **DECISION, Sadri's, and it reverses the porting principle: iOS standards are the priority; the mockups are reference, not spec.** *"Don't be strict to the mockup, mockup is just another CSS style… the real iOS design is priority."* Every ported screen migrated in one pass.

  **What the mockups still settle, and it is not a small list:** what is on each screen, in what order, what outranks what, which surface a thing sits on, the colour tokens (a hex is a hex — `Palette` is unchanged and still mirrors `shared.css` exactly), the typeface (SF Rounded, the mockups' `ui-rounded`), the copy, and every argued-out structural decision — the eyebrow row, the transparent sheet, the pinned one-row footer, list-not-chip-row. **What they no longer settle: how big anything is.**

  **What was wrong, measured.** Every screen used to set type as `.system(size: mockupPx * screenWidth / 242)`. Two consequences:
  1. **Type grew with the screen.** Body text came out 17.8pt on an SE, 18.7pt on a 16, 20.9pt on a Pro Max — where the platform answer is 17pt on all three. A Pro Max became a magnified SE instead of showing more, which is the opposite of the iOS layout model. Sadri's exact objection, and it was correct.
  2. **Dynamic Type was a silent no-op.** A computed `.system(size:)` ignores the reader's text-size setting, so every accessibility text size did nothing anywhere in the app. That is an accessibility failure, not a style choice — and it is why the deferred "longest-real-string pass at the largest accessibility size" item could never have passed.

  A third defect nobody had noticed: **the aspect-ratio assumption breaks on SE.** The mockup frame is 242x532 = 2.20:1. iPhone 16 and Pro Max are 2.17:1, close enough — the SE is 375x667 = **1.78:1**. Scaling by width there wants 824pt of height on a 667pt screen, 157pt too tall. Screen 05's radar alone would have been 310pt, 46% of the SE's screen, before the app bar, stages and footer.

  **What replaced it,** in `Core/Theme.swift`:
  - **`AppFont`** — every face built on a semantic `Font.TextStyle` with `design: .rounded`, so it scales with the reader's setting. Named by ROLE, not size: `screenQuestion`, `wordmark`, `placeName`, `barTitle`, `controlLabel`, `factValue`, `listTitle`, `bodyText`, `bodyEmphasis`, `secondaryLabel`, `tag`, `inlineAction`, `chip`, `note`, `microLabel`, `fineprint`. The mockup's HIERARCHY is preserved exactly; each rank is mapped onto the nearest native style.
  - **`Metrics`** — 4pt grid, `margin` 20 (Apple's readable-content inset; the mockups' 22-of-242 was 9% of width and came out 34-40pt), `tapTarget` 44, `controlHeight` 50, `hairline` 1, `cornerSmall` 16, `cornerLarge` 28.
  - **`GlyphMetrics.stroke(_:grid:size:)`** — replaces `MockupScale.gridStroke`, and no longer routes through a screen-width factor.
  - **`MockupArt.width(_:in:)`** — the one thing the old approach got RIGHT, kept and narrowed to artwork only. The supergraphic band, the home illustration and the radar are COMPOSITIONS, not sizes: the band is authored as `height = width x 0.826` and its crop at both edges is the entire idea of a supergraphic. Freeze it to points and it stops bleeding on a wide screen and overflows on a narrow one. **So the rule is a split: art scales with the screen, anything a reader reads or touches does not.**

**The three slots have different technical requirements, verified against current docs rather than assumed** (`apple-hig.md` flags icon guidance as the one part that has moved twice, so this was checked, not recalled):

| Slot | Background | Content | Alpha |
|---|---|---|---|
| Any Appearance | **opaque** blush `#F7F1EF`, full-bleed | mark in `#A6243D` | **none** — App Store rejects an alpha channel here |
| Dark | **transparent** — the system draws its own dark ground | mark in `#F58396` | yes |
| Tinted | **transparent** | **grayscale** (white mark) — the system maps luminance through the user's chosen tint | yes |

Verified on output: `alpha=False` on Any, `alpha=True` on the other two, all `1024x1024` sRGB. The clock counter is a genuine hole, so in Dark and Tinted the system background shows through it — checked by compositing over `#1C1C1E` and a simulated tint.

**Tinted is white-on-transparent**, which gives the brightest, most saturated tint. If it reads too hot on device, re-render the mark at a lighter gray (~`#D8D8D8`) — that is the only knob, since a flat mark has no internal luminance range for the gradient to work with.

**Worth flagging: this is the pre-Icon-Composer path.** Flat PNGs in an asset catalog are still fully supported, but they get **none of the Liquid Glass layering** — no system specular highlights, no clear variant — which is precisely what the layered Icon Composer build in [[portfolio-art-direction]] was chosen for. Reasonable as a way to get the mark onto a device *now* (and the fastest route to closing the outstanding **29pt device test**), but the `.icon` build is still the one to ship for a portfolio piece whose whole pitch is current-iOS craft. ## 2026-09-17 — Screen-to-screen transition animation

- `RecommendationView` swapped screens instantly because a bare `switch` in a body reconfigures one render-tree node rather than inserting/removing views. Fixed with the three pieces a SwiftUI transition actually needs: a `Group` to hang the wiring on, `.id(screen)` to force an identity change, and `.transition` + `.animation(_:value:)`.
- Animation is driven from the View, not the ViewModel. Wrapping the eleven `state = …` writes in `withAnimation` was the alternative and was rejected — it puts presentation timing inside the ViewModel, against the project's one architectural rule.
- `State` can't be the animation key (`.loaded` carries a non-`Equatable` `RecommendationResponse`, and a photo landing mid-result would re-fire the transition). Added a private `Screen` token that collapses state to "which of the six screens is showing". It must be `Hashable`, not just `Equatable` — `.id()` requires it — and the conformance is hand-written because the `.networkError` payload (`NetworkErrorVariant`) is `Equatable` only, which blocks synthesis. Writing it out kept the fix inside this file instead of widening another feature's enum.
- Motion follows [[visual-identity]] → Motion: asymmetric, insertion is opacity + scale from 0.98 (the specified ≈0.2–0.3s "pop", set at 0.28s), removal is a plain fade so the overlap doesn't read as a zoom-through. Reduce Motion degrades to a 0.2s crossfade, per the same rule.
- **Follow-up, same day:** the first build animated the background only. Cause: every screen's root is a `GeometryReader`, which republishes its size to its children on each frame of a scale, so content re-laid-out at every intermediate size instead of scaling as one unit — only the flat `Color.bg`, having no layout to recompute, appeared to move. Fixed by isolating the subtree's geometry before the transition. `geometryGroup()` is the correct modifier but is iOS 17+ against our 16.0 target, so a small `screenGeometryGroup()` helper branches on availability and falls back to `transformEffect(.identity)` — the known iOS 16 stand-in, load-bearing rather than a no-op. Order matters: it must be applied *before* `.transition`, so it wraps the screen rather than the transition.
- **Verification note:** a bare `swiftc -typecheck` is useless on this project — it can't resolve the SPM packages, fails at the import stage, and never checks function bodies (this is how a `Hashable` error slipped through). Point it at the built modules instead: `-I`/`-F` at `DerivedData/hungrynow-*/Build/Products/Debug-iphonesimulator`, and match their arch with `-target x86_64-apple-ios16.0-simulator`.
- **Correction to the two entries above:** the `GeometryReader` diagnosis was wrong, and the geometry work did not fix the symptom. The actual cause was **modifier order**: `.id(screen)` was applied *outside* `.transition(...)`. Modifiers apply inside-out, so the identity change tore down the whole subtree including the transition modifier — leaving nothing to animate, and only the flat `Color.bg` appearing to move. Correct order, bottom-up on the `Group`: `.id(screen)` → `.screenGeometryGroup()` → `.transition(...)` → `.animation(_:value:)`. `.id` must sit UNDER `.transition` so the transition still describes the screen whose identity changed.
- `screenGeometryGroup()` is kept — it is still correct for stopping mid-animation re-layout inside each screen's `GeometryReader` — but it was never the blocker. Testing is on an iOS 26 simulator, so the `#available(iOS 17, *)` branch runs the real `geometryGroup()`; the iOS 16 `transformEffect` fallback is untested on device.
- **Root cause, after three wrong diagnoses:** `.animation(_:value:)` cannot drive this transition at all. The body switched on `viewModel.state`, and an `@Published` change rebuilds the body wholesale — the modifier then sees the new value already in place, with no prior value to interpolate from, so no animated transaction is created and the screens snap. Neither modifier order nor `GeometryReader` was the blocker (both earlier "fixes" were kept, being independently correct, but neither changed the symptom).
- **Working approach:** mirror the state into the View's own `@State private var screen`, write it inside `withAnimation` from `.onReceive(viewModel.$state)`, and switch the body on that. The explicit transaction is what `.transition` attaches to. The ViewModel is still untouched — the animation lives entirely in the View, so the no-UI-logic-in-ViewModel rule holds.
- `Screen` now carries the `RecommendationResponse` payload (the body binds it) but hashes on the case name ONLY, so a hero photo arriving mid-result does not re-fire the transition. `ResultView` still updates on new photos because it reads `viewModel.heroPhotos` directly.
- **Confirmed working** by Sadri on the iOS 26 simulator: the mirrored-`@State` + `withAnimation` approach animates the six recommendation states.
- Applied the same pattern to `App/RootView.swift`, which had the identical instant-swap on its `Route` switch (Welcome → Recommendation). Simpler there — `route` is already local `@State`, so no mirroring is needed; the writes just had to go through a new private `go(to:)` that wraps them in `withAnimation`. All three call sites converted, and `Route` gained `Hashable` for `.id` and the no-op guard.
- Extracted the shared motion vocabulary to **`Core/ScreenTransition.swift`** (`ScreenTransition.transition(reduceMotion:)`, `.animation(reduceMotion:)`, and the `screenGeometryGroup()` View extension). It was private to `RecommendationView`; two layers now need it (App shell + Recommendation feature), and duplicating it would let the two screens' motion drift apart. New files need no `.xcodeproj` edit — the project uses `PBXFileSystemSynchronizedRootGroup`.
